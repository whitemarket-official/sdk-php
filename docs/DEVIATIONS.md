# Deviations from SDK_SPEC (PHP)

Every place where this SDK deviates from [`SDK_SPEC.md`](SDK_SPEC.md), with the reason (CLAUDE.md rule 17).

| Spec section | What the spec requires | Why it does not fit PHP (fact) | What this SDK does |
|---|---|---|---|
| 1.1 "Generated public surface: all ... input ... types" | Every input field is generated | A `FileUpload` value is a multipart upload; the transport sends JSON only. The one such field, `PersonStoreInput.customAvatar`, has a JSON alternative `encodedCustomAvatar` | `FileUpload` input fields are not generated (ADR 0002 "Implementation notes") |
| 1.5 "Errors" | `HttpError`, `ServerError` and `GraphQLError` are thrown directly for the cases no subclass covers | The project formats with php-cs-fixer `final_class` (every concrete class is final, no exceptions configurable), so a thrown class cannot also be a parent | `HttpException`, `ServerException` and `GraphQLException` are abstract parents (catch them as the spec says); the uncovered cases throw the final leaves `GeneralHttpException`, `GeneralServerException`, `GeneralGraphQLException`. `WhiteMarketException` is abstract. `DecodeError` is `Errors\DecodeException` (PHP naming). One entry of `errors` is `GraphQLErrorEntry` (the spec gives it no name; `GraphQLError` is the exception there; proposed for SDK_SPEC). `LiveConnectionError` is `Errors\LiveConnectionException` (PHP naming) |
| 1.5 "Errors" | `NotFoundError` when "category ends with `.not_found`" | The spec does not say which error of a multi-error response decides | `NotFoundException` only when every error's category ends with `.not_found`; a mix gives `GeneralGraphQLException` (`GraphQLException::hasCategory()` finds a category in any error). Proposed for SDK_SPEC clarification |
| 8 "Security" | Secrets never appear in logs or debug output | A credential arrives as a string in the response body; while it is parsed, internal functions (`json_decode`, `preg_match`, the `SensitiveParameterValue` constructor) receive it as a plain argument, and PHP cannot mark their parameters. A backtrace taken in that instant (an async signal handler, a PHP 8.5 `max_execution_time` fatal with `fatal_error_backtraces`) shows it | Out of the threat model (owner decision 2026-10-31): `Secret` hides the value in every steady-state inspection and SDK parameters carrying credentials or raw bodies are `#[\SensitiveParameter]`; transient frames of internal functions during parsing are not covered |
| CLAUDE.md "No static mutable state" (`Export\Rows\BodyStreamWrapper`) | A static registry of the bodies being read by `ext-yajl_stream` | PHP instantiates a stream wrapper itself and passes only the URL, so the body must be found by a key | Random 128-bit id per stream, entry removed on close (also when the iterator is dropped); internal class, used only by `YajlStreamRows` |

| 3.10 rule 12 (`JsonStreamDecoder::YajlStream`) | Every JSON parser refuses a row nested deeper than 511 levels (512 with the enclosing list) | ext-yajl_stream 0.1.0 has no depth limit: a row nested 200000 levels (about 400 KB) is built, then PHP segfaults when the array is destroyed. The 128 KiB row cap limits a row to about 65000 levels; 131000 levels built and were destroyed without a crash [observed 2026-11-01, PHP 8.5 image, 8 MiB stack]; a smaller C stack (threads, ZTS, a lower `ulimit -s`) may still crash. Also reached under `Auto` when the extension is loaded. json-machine (`ExtJsonDecoder` depth 512) and the simdjson path refuse it | Pending: a max-depth option in ext-yajl_stream (owner decision 2026-11-01); the SDK then requires that version and passes 512. Until then the export host is trusted not to send such a row; pick `JsonMachine` or `Simdjson` if that matters |
| 3.10 rule 11 (CSV, `Export\Rows\CsvRows`) | RFC 4180 values; an empty line is skipped | PHP `str_getcsv()` drops trailing CRs of an unquoted field (`x\r,y` gives `x`) [observed 2026-11-01, PHP 8.5]; only one CR directly before the LF is a line end, so a line `\r\r\n` is a record holding `\r`, not an empty line | An unquoted value cannot end in a CR (quote it to keep one); a line of only CRs is read as a record (one empty value: a row with a one-column header, a field-count `DecodeException` otherwise). Extra CRs count against the 128 KiB record cap |
| 3.11 (SSE read latency) | An event is delivered as soon as the server sends it | On a chunked SSE body PHP's dechunk filter holds data for up to one read slice (`LiveOptions::$readSlice`, 1 s) [observed 2026-11-01, PHP 8.5.4 and 8.2.35, adversarial-verifier on the L2b spike] | SSE events on a chunked response may arrive up to one slice late; WebSocket is the default and has no such delay (README "Live updates") |
| 3.11 (deadlines of `poll()` / `run()`) | A blocking call returns by its deadline | A Guzzle stream read cannot be interrupted inside a slice, and phrity reads a frame with one socket timeout per `fread` [`vendor/phrity/websocket/src/Frame/FrameHandler.php:192-206`], so a server trickling a frame one byte per gap held `poll()` for payload length times the gap [observed 2026-11-01, `poll(2.0)` took 50 s] | WebSocket: `Live\WebSocket\DeadlineSocketStream` (the captured socket stream) fails every read after an absolute deadline: the read deadline plus the idle seconds (ping + 10 s), checked before each socket read; the read ends with a `TransportException`, the partial frame is dropped and the session reconnects with backoff. Bound: read deadline + idle seconds + one socket-read gap. SSE: a read overruns its deadline by at most one slice (`readSlice`, 1 s), the deadline is checked between slices |
| 3.11 (connect deadline) | The connect attempt is bounded by the open deadline | The WebSocket handshake runs inside phrity `Client::connect()` under the socket timeout set from the idle timeout (35 s), and its HTTP reader (`HttpHandler::readLine`) restarts that timeout per `fgets` | `connectTimeout` covers the TCP connect; the upgrade response is bounded by the open deadline plus the idle seconds through `DeadlineSocketStream` (one byte per `readLine` call so the deadline is checked between bytes), plus one socket-read gap |
| 1.5 "Errors" (live internals) | Network failures of the live transport are `TransportError` | `TransportException` is final (public API), so the internal close and connect-reject signals cannot extend it | `Live\ServerClosed` (close code, sanitised reason) and `Live\ConnectRejected` (connect error code) are internal `WhiteMarketException`s; `LiveSession` catches `TransportException|ServerClosed|ConnectRejected` and only `LiveConnectionException` reaches the caller |
| 3.11 (close reason in the exception message) | `LiveConnectionError` carries the code and the reason | The reason is server text (SDK_SPEC 3.11) | `LiveConnectionException::$reason` holds it; the exception message names the code only (a message is often logged), callers branch on `closeCode` |
| 3.11 (TLS only) | Live connections use `wss` / `https` only | The internal `WebSocketConnection` maps an `http://` base to `ws://` so the local test fixtures can run without TLS | Unreachable through the public API: `TransportOptions::$baseUrl` is https-only (`OptionRules::assertHttpsOrigin`) and `WhiteMarketClient::live()` passes it; only a direct construction of the `@internal` class reaches plain `ws://`. A temporary connect rejection (`Live\ConnectRejected`, code + `temporary`, no server text) reaches `onError()` handlers |
| Plan T7.2 (`docs/plans/2026-10-30-sdk-v0.1.md`) "codeql" workflow | A CodeQL workflow in `.github/workflows/` | CodeQL has no PHP support (its languages are C/C++, C#, Go, Java/Kotlin, JavaScript/TypeScript, Python, Ruby, Rust, Swift, GitHub Actions; PHP not listed) [docs: https://codeql.github.com/docs/codeql-overview/supported-languages-and-frameworks/, checked 2026-11-01] | Not added. Static analysis is PHPStan level max plus the custom rules in `tools/phpstan`, gitleaks (`make secrets-scan`) and `composer audit` |
| SDK_SPEC 1.2 selection of a deal's product item (`MarketProductHistory.params`) in `deal_history`, `deal_history_item`, `deal_item`, `deal_buyer_list`, `deal_seller_list`, `market_buy`, `market_new_multiple`, `market_edit_multiple`, `market_remove`, `market_remove_multiple`, `deal_request_cancel`, `deal_cancel_sending_offer`, `deal_steam_offer_sent` | `params` selects every leaf of `CSGOInventoryItem` (`updatedAt` included) and `order { id }` | The server answers `params.updatedAt` with "Internal error occurred" (no category) and, once that field is gone, `params.order { id }` with HTTP 500 [observed 2026-11-01, field-by-field on `deal_history`]. A mutation is rolled back with it: `market_buy` answered the error at `market_buy.product.params.updatedAt` and created no deal, the listing stayed (2 of 2 purchases, 2026-11-02); the SDK correctly reported an unknown outcome. So history, the archived `deals->get()`, buying and every deal-returning mutation failed live | Hand-written overrides in `graphql/overrides/` drop both fields there (no model uses them); `tests/unit/Generated/ProductHistoryParamsSelectionTest.php` fails if any operation selects them again (schema sync). Live after the fix: `deals->history()`, the archived and the in-progress `deals->get()` work, and `buying->buyProduct()` created a deal that reached EXCHANGED (2026-11-02). Backend to be told |
| SDK_SPEC 3.7 `orders` (plan T4.2) | The high-level `orders` module (create, edit, activate, deactivate, delete, mine*, search, iterators) | The schema declares `MarketOrder` / `MarketOrderPublic` as interfaces with no possible type, so every generated `order_*` operation selects only `__typename` and returns no order data; the generator fix is proposal P14 (`docs/plans/2026-10-30-sdk-spec-proposals.md`), awaiting the owner | Not shipped in 0.1.0: `WhiteMarketClient` has no `orders`; the generated `order_*` methods exist in `GeneratedClient` |

## Accepted limitations

Known gaps the owner accepted as they are (decision 2026-10-31); revisit when one of them starts to matter.

| Area | Gap | Why it is accepted |
|---|---|---|
| `Export\Rows\BatchJsonRows` vs `JsonMachineRows` / `YajlStreamRows` (SDK_SPEC 3.10 rules 9, 12) | On a broken JSON body only, the parsers may differ by one row: for `[A x,B]`, `[A B]` or `[A` cut off, json-machine and yajl deliver `A` and fail at `products[1]`, the batch decoders (simdjson, `json_decode`) deliver nothing more and fail at `products[0]`; likewise a cut after `[{...}` with a short `Content-Length` | Our scanner cuts a row at the next `,` or `]` at depth 1, the libraries emit a value as soon as it closes [observed 2026-11-01, adversarial-verifier round 5]; a valid body gives identical rows on every parser; matching each library's error semantics in the scanner costs much code for corrupt input (owner decision 2026-11-01) |
| `Errors\BodyRedactor` | Running out of memory while decoding a valid JSON error body (up to 1 MiB) prints its first bytes (`zend.exception_string_param_max_len`, 15 by default) in a PHP 8.5 fatal error backtrace; on PHP 8.2 (no `json_validate()`) a malformed body that starts with `{` or `[` still reaches `json_decode()` and its caught `JsonException` holds the body in its trace. `cutAtFirstMarker` has the same exposure for its 512-byte cut | Needs an out-of-memory fatal or an exception hook that reads caught exceptions; the body start is JSON structure in practice |
| `tools/phpstan` `SensitiveParameterInheritanceRule` | Not reported: a child variadic that starts before a parent's variadic sensitive parameter; a method inherited from a parent class that does not implement the interface marking it (`Impl extends Base implements Exec`); an ancestor attribute spelled in a different case | No such code in `src/`; stock `class.nameCase` reports the spelling |
| `tools/phpstan` `SensitiveCallbackRule` | Only the listed functions are checked: not `array_find*`, `array_any`, `array_all`, the `array_u*` / `*_ukey` / `*_uassoc` family, `forward_static_call*`, `mb_ereg_replace_callback`, method calls (`Closure::call`, `Reflection*::invoke*`, `ArrayObject::uasort`), closures with their own sensitive parameter, plain functions | None of these is used in hand-written `src/` |
| `Models\ModelMapper` (trace arguments) | The public mapping methods (`deal`, `archivedDeal`, `walletTransfer`, `profile`, the `*Page` methods and the rest) take the decoded server result as a parameter without `#[\SensitiveParameter]`. When a result fails to map (a malformed decimal, a missing field), the `DecodeException` keeps that result in its trace arguments, and with it what the server echoes: `receiverTradeUrl` of a deal, `steamTradeUrl` of the profile, the recipient of a transfer. Such a `DecodeException` also arrives as `getPrevious()` / `lastLookupError` of `PurchaseOutcomeUnknownException` and `MutationOutcomeUnknownException`. Found by adversarial verification (session 17) | Owner decision 2026-11-01: needs a malformed or drifted server response and trace arguments switched on (`zend.exception_ignore_args=0`); the values are the account's own data from the server, not credentials. The trade URL and recipient the caller passes in stay masked in SDK frames (`BuyingApi::reconcile()`, `WalletApi::failure()`, `RetryLoop::run()` closures) |
| `Errors\GraphQLException` | `getMessage()` holds the server's `errors[0].message` and `category` verbatim; `extensions` and `partialData` are public raw values; `ErrorCategory::isNotFound()` parameter is not `#[\SensitiveParameter]` | The message is what callers need to act on; the server is not expected to echo credentials in GraphQL errors |
| Generated models | `fade` is `?float` in 29 generated classes | Not classified as a wear value (CLAUDE.md rule 3) yet; if it is, a decimal-string override in `graphql/overrides/` is the fix |
| `tools/docker/php.Dockerfile` | Base image, `pecl` and `apt` packages are not pinned | Used only by local and matrix runs, never shipped |
| `Transport\HttpTransport` (trust boundary) | Injected PSR-7, PSR-17 and PSR-18 implementations are trusted with the credentials and the request body. Not wrapped: a request object whose destructor throws (it runs when `request()` replaces or releases a clone, outside any `try`); a stream factory failing on the body. Also trusted, not wrapped: PSR-17 request and stream factory failures and PSR-7 request-method failures (`createRequest`, `withHeader`, `withBody`, `createStream`); they run before anything is sent, so they cannot cause a double execution. Each can carry the credential or the body out of `post()`. Guaranteed: no credential in SDK messages or SDK frame arguments (every closure parameter of `RetryLoop::run()`, since each captures the client, and the request parameters are `#[\SensitiveParameter]`); every call on a client-provided object is wrapped: `sendRequest()` by `RetryLoop::sendVia()`, every method of the response and of its body stream by `Transport\ClientResponse` / `ClientStream`, so any Throwable they throw (an SDK exception such as `AuthenticationException` included, an `Error` too) leaves as an unchained `TransportException` naming the class only and no exception from client code reaches the 401-replay or `MutationRejection` (a mutation is neither replayed nor classified as a clean rejection); whatever the request throws while a credential header is set leaves as an unchained exception without the value. The residual is only what a client does with the credential it receives by design | Needs a non-default implementation that breaks PSR-7/PSR-18; code that receives the credential by design can leak it in many other ways the SDK cannot prevent (owner decision 2026-10-31) |
| `GraphQL\GraphQLExecutor` (success body) | A 2xx body up to `maxResponseBytes` (32 MiB by default) is decoded with `json_decode`; a large body can exhaust `memory_limit` (128M by default) after a mutation ran: the PHP fatal error cannot be caught, so `buy*` ends without a BuyResult or PurchaseOutcomeUnknownException and an SDK-generated customId is lost | Needs a faulty or hostile server; lower `TransportOptions::maxResponseBytes` to bound it; callers that must never lose a purchase pass their own customId and persist it before calling (README, T7.1). Owner decision 2026-11-01 |
| `Transport\SafeLogger` | A logger whose thrown exception object's destructor throws again escapes SafeLogger (the destructor runs after the catch); a hostile logger could so turn a finished `market_buy` into an exception that looks like a rejection | Injected PSR-3 implementations are inside the same trust boundary as PSR-7/17/18 (row above); needs deliberately hostile code. Owner decision 2026-11-01 |
| `Transport\ClientResponse` / injected PSR-18 objects | A response, body stream or thrown exception object of an injected PSR-18 client whose `__destruct()` throws runs that code when PHP releases the object, which can be inside an SDK frame (after `RetryLoop::run` returns, on retry/redirect reassignment): it can escape raw, and an `AuthenticationException` thrown that way can make `GraphQLExecutor` replay a mutation or be read as a rejection | Needs deliberately hostile injected code (same class as the `Transport\SafeLogger` row); every method call on client objects is wrapped. Owner decision 2026-11-01 |
| `Models\Paginator` | `Paginator.php:41` stops only on a cursor repeated by the adjacent page (`endCursor === $cursor`); a cycle A -> B -> A with `hasNextPage = true` loops forever | Owner decision 2026-11-01: a correct server never returns a cursor cycle |
| `Auth\PartnerTokenProvider` (single-flight) | No lock across processes: workers sharing a `TokenStore` that find the token expiring at the same moment each call `auth_token` once; in one process a Fiber-based PSR-18 client could interleave two refreshes | PSR-16 has no atomic `add`, a lock would need a backend-specific dependency; the cost is a rare extra `auth_token` at expiry (owner decision 2026-10-31, ADR 0003) |
| `Transport\HttpTransport` (gzip) | A gzip body of several concatenated members is read up to the end of the first member; the rest is ignored | HTTP servers send one member; decompression stays bounded and simple (owner decision 2026-10-31) |
| `Transport\RetryAfter` | Three valid `Retry-After` HTTP-dates parse as "no header", so a 429/503 query is retried as without one: a leap second (`23:59:60`); an RFC 850 two-digit year read through PHP's fixed 1970-2069 window instead of RFC 9110's "more than 50 years ahead means the past century" (in 2026: years 70-76); a repeated header joined as `120, 120` (no list form defined, so invalid anyway). Never a wrong number: the round-trip check rejects them | Servers do not send leap seconds, RFC 850 has been obsolete since 1996 and the window only differs for dates 44-50 years ahead; queries only, bounded by `maxAttempts` (owner decision 2026-10-31) |
| `schema/partner.graphql` | Public-doc `@example` text contains Steam-ID-shaped numbers and `1.2.3.4` | Example values from the public partner docs; the file is a server snapshot, never edited by hand |
| 1.3 "Export downloads" / ADR 0002 `allow_redirects` row | The default Guzzle client follows at most 3 same-host https redirects (`allow_redirects` with `max`, `strict`, `protocols`) | Guzzle's PSR-18 `Client::sendRequest()` sets `allow_redirects` to `false` for every request, over the client configuration (`vendor/guzzlehttp/guzzle/src/Client.php:193-195`, 7.16.1) | `Export\ExportTransport` follows redirects itself (max 3, https, same host and port, no credentials in the URL) for the default client, whose own redirects are off (`allow_redirects` false in the config). An injected PSR-18 client that follows redirects internally (e.g. Symfony `Psr18Client`, default `max_redirects` 20) is outside this rule: the SDK never sees the hops (the trust-boundary row above) |
| `Export\ExportTransport` (identity chunked body) | An identity body sent with `Transfer-Encoding: chunked` and cut before its final chunk is read as a complete file | PSR-7 exposes no framing: the stream ends at EOF whatever the cause. A body with `Content-Length` is checked (exactly that many raw bytes, `Transport\BodyReader`) and a gzip body must reach its end marker | Not detectable through PSR-7; a caller that needs a guarantee compares the result with `meta()->items` |
| 1.4 "Export GET" retry / 1.3 export responses | Export GET retried on network error, 5xx, 429; the file is any 2xx | `RetryPolicy::shouldRetryRead()` retries every 500-599 and 429 (a query keeps 429/500/502/503/504); only a 200 is a file (304 for a conditional call): 206, 202, 204 are an `HttpException` (precedent: 304 of an unconditional call). A client-thrown exception of any type, from `sendRequest()`, the response or its body stream alike (`Transport\ClientResponse`), is a `TransportException`; only a PSR-18 network error from `sendRequest()` is retried | A 206 is a range and 202/204 carry no complete file, so a partial body must not replace the old file; not covered by the spec text, proposed in P18 |
| `Transport\BodyReader` (Content-Length) | A `Content-Length` that is not one plain number is ignored | RFC 9110 8.6: identical repeats are one value; absent: no check; anything else (`+1000`, `1000, 999`, letters, empty) fails a strict read with a `TransportException` (an error excerpt stays lenient). The same for every encoding: a gzip body is counted in raw (compressed) bytes, and bytes after the gzip member are read and dropped (or refused by an export read) so the count is complete | A server sending a malformed length on a 2xx fails the call instead of passing unchecked |
| `Export\PriceRow::$extra`, `Export\ProductRow::$extra` | Values of unknown keys are as `json_decode` returns them: big integers as strings (`JSON_BIGINT_AS_STRING`), decimals possibly as PHP floats; the known fields never are (decimals are strings parsed to `Decimal`) | `extra` is raw by design (a new server field is never an error); typing it would need the field's meaning | Money and wear are read from known fields only; do not compute with `extra` values |
| 1.3 "Export downloads: idle timeout 60 s" | An idle (read) timeout and a connect timeout on the default client | Guzzle applies `read_timeout` only in its stream handler (`Handler/StreamHandler.php:505-509`), which serves `stream` requests while `allow_url_fopen` is on (`Utils::chooseHandler()`); the stream handler has no `connect_timeout` (PHP's `default_socket_timeout` applies) and takes `read_timeout` fractions wrongly (`* 100000` instead of `* 1000000`, line 507); the cURL handler ignores `read_timeout`, and the `curl` option is deprecated for the stream handler (line 706) so cURL low-speed options cannot be added | `GuzzleClientFactory::exportConfig()` sets `connect_timeout`, `read_timeout`, `stream`; with `allow_url_fopen` off or a user client, idle and connect timeouts are the client's own |
| `Export\Rows\JsonMachineRows`, `YajlStreamRows` (SDK_SPEC 3.10 rule 10) | Bytes after the closing `]` of the products array (`[...]x`) are not checked; the rows before are returned. `Simdjson` (own scanner) refuses them | json-machine 1.2.6 and ext-yajl_stream 0.1.0 stop at the end of the root array [observed 2026-11-01]; the body's own completeness is checked (Content-Length, gzip end, no data after the gzip stream) (owner decision 2026-11-01) |
| `JsonStreamDecoder::YajlStream` (SDK_SPEC 3.10 rule 12, CLAUDE.md rule 3) | A products row whose id is above `PHP_INT_MAX` fails with `DecodeException` (also under `Auto` where ext-yajl_stream is loaded) instead of arriving as a digit string | ext-yajl_stream 0.1.0 turns such an integer into a float (`cb_number`); the mapper refuses a float id, so no digit is ever lost; Steam ids are far below 2^63; `JsonMachine` / `Simdjson` keep them (owner decision 2026-11-01) |
| `Live\Sse\SseConnection` (`var_export`) | `var_export()` of an internal open SSE connection prints the request object and so the request URL (with the access token in the query); `print_r`, `var_dump` and `var_export` of `Secret` stay masked, `print_r` / `var_dump` of the connection are masked, and trace arguments are masked by the PHPStan rule | `var_export` ignores `__debugInfo`; the class is `@internal`, built only by `LiveFactory`, and not reachable from the public `Live` handle by a dump | Not covered; do not `var_export` internal objects |
| `Live\WebSocket\DeadlineSocketStream` (phrity `FrameHandler::read()`) | A frame whose last unread byte is exactly `0` and arrives alone in its own read fails the connection (`Empty read; connection dead?`) | phrity 4.1.0 `Frame/FrameHandler.php` ~:200 `if (empty($got))` treats the read result `"0"` as an empty read [code]; the stream extends a lone `"0"` by one more read whenever phrity asked for more than one byte, so only a request for exactly one byte can still get a bare `"0"` (the last byte of a payload that ends in `0` and trickles in) | Upstream bug, residual case (length 1) not fixable below phrity; the session reconnects with backoff |
